# Proposed first runtime boundary

Status: an explicitly selected local experimental mode connects the worker, owner-authenticated HTTP API and UI to the runtime. It is under review and is not production-ready. Both `--demo` processes remain simulations and do not contact a container daemon. The adapter and backend flow have been exercised against a fake Engine and one dedicated rootless Engine in OrbStack; the observations and their limits are recorded below. A desktop Chromium flow has also been exercised against that daemon; mobile UI tests used a simulated provider.

The experimental `dockerlocal` adapter uses an explicitly supplied Unix socket, checks its owner and permissions, and requires a non-root process and private parent directory. It rejects symlinks and ancestors owned by other accounts or writable by group or others; this deliberately rejects sockets under shared writable directories, including sticky directories such as `/tmp`. These mode checks do not verify filesystem ACLs and are not atomic against concurrent replacement; the socket and path must remain under the dedicated account's exclusive control and ACLs must not grant untrusted access. It makes no use of the Docker CLI, environment discovery, proxy, or redirects. Calls use bounded responses and deadlines, and errors never include daemon responses. The adapter requires Engine API 1.47, a Linux rootless daemon reporting seccomp, cgroup v2, systemd and memory, CPU and PID controls. Engine-reported capabilities are not proof that enforcement actually works. A dedicated daemon and account are operational requirements, not properties the API can establish.

Resources use deterministic names derived from the three owner IDs; ownership labels and the effective restrictions are checked before any mutation, which is directed at the full inspected container ID. A repeated create returns the observed state, including a stopped or partially created state; it does not restart it. Images must already exist locally by digest and images declaring volumes are rejected. Container logs and networking are disabled. The implementation needs a broader independent security review and further Linux rootless testing before production use; a fake server cannot establish kernel isolation, effective resource limits or daemon semantics.

## Scope and authority

The proposed first provider is a dedicated Docker Engine in rootless mode on Linux, accessed only through an explicitly configured private Unix socket. Never discover a default socket, `DOCKER_HOST`, Docker contexts or credentials. The service account must be dedicated to this installation; access to its socket grants authority over that daemon, not a fine-grained security boundary. Protect the socket and parent directories and do not share the daemon with other tenants. Rootless mode reduces host privilege but does not replace host isolation or a supported kernel and daemon configuration. See [Docker rootless mode](https://docs.docker.com/engine/security/rootless/) and [protecting daemon access](https://docs.docker.com/engine/security/protect-access/).

The initial resource is one container from a locally present image pinned by SHA-256 digest. Images are never pulled implicitly: the owner may explicitly download a public image by digest (`POST /image/pull`), and `GET /image` may ask the registry, through the daemon, for a tag's current digest and an image's platforms. Neither sends registry credentials, and daemon messages are reduced to fixed categories. Creation checks the image is present, matches the daemon platform and declares no volumes before persisting any intention, so a missing image no longer consumes the single initial operation. There is no build, registry credential, host port, URL, volume, bind mount or shared host namespace. Networking is disabled. The experimental UI reports the service observation and may explicitly request a fresh inspection; the current UI's simulated deployments do not become real deployments.

## Interface and identity

The provider-neutral interface has four operations: create and start, inspect, stop, and remove. Each request is scoped by installation, service and operation IDs, all generated by Dársena. The operation ID identifies one immutable specification. Repeating it with the same specification is idempotent; changing the specification is a conflict. A reference includes all three IDs and the provider resource ID, and ownership must be verified before inspection or mutation. A matching name alone is insufficient. There is no API for arbitrary provider options.

Creation returns a reference and observed state when these are known, including when creation succeeded but starting failed. A response lost after an external request has an **unknown outcome**. Cancellation before an operation begins produces no effect; cancellation or timeout after dispatch cannot prove absence of effects. Inspect by stable identity before any retry. Stop is repeatable; removing an absent owned resource is repeatable, but a running resource must first be stopped. Errors are fixed categories and must not include request values, daemon response bodies, environment, or secrets.

Configuration values remain absent from `Spec`, references and persistent intent. The experimental worker accepts a revision-bound snapshot and passes its values to the Docker adapter in memory through the persisted execution coordinator. Do not log values or pass secrets in process arguments. A revision identifier alone does not prove that a provider applied its values.

## Configuration and revision policy

Saving configuration does not automatically restart, replace or alter an existing service. The UI shows the accepted revision and explains that later changes affect only a future explicit creation. This initial mode supports one initial service operation per application; recreation and rotation controls are not yet implemented. The UI exposes separate stop and confirmed removal actions; removal preserves the saved definition and configuration. A stopped or created container can be removed, but a running one must first be stopped.

Stop and removal have separate persisted action records, dispatched using conditional transitions before the provider is called. Repeating an action does not dispatch it again. If its result is unknown, an explicit refresh inspects the provider and records the observation; absence never authorizes another creation. The standalone generic recovery pass does not yet recover these action records automatically. The intent store migrates from schema v1 to v2 for actions, and offline backup validation accepts both versions.

A creation request must name the revision the caller reviewed. `Vault.Accept` reads the current revision and encrypted document together, accepts only the requested positive revision, and returns a fixed conflict when it is absent or differs. Its isolated snapshot retains the accepted values after later updates. `runtime/configbridge` checks its resource and revision. The worker invokes `runtime/execution.CreateConfigured` accepts and validates the snapshot before the conditional dispatch claim; only its winner calls the configured provider. Existing dispatched or observed intentions are not resent. The accepted revision is metadata, never a request to silently substitute a newer revision or automatically retry a conflict. A change committed after acceptance may race with dispatch: SQLite and Engine do not share a transaction, and the accepted revision is not guaranteed to remain the latest when Engine creates a container. A later check is not an atomic guarantee; conflicts require an explicit decision and are not retried automatically.

Public variables and secrets are not supplied to `runtime.Spec`; the vault's public view hides secret values. The accepted snapshot has private fields and redacted formatting, JSON and structured logging; explicit visitation supplies values only to the internal consumer. Its receiver is trusted: the interface cannot prevent a receiver from retaining or logging values. Values exist in memory as Go strings and cannot be reliably erased. The configured adapter constructs the Docker environment in memory, with a 256 KiB serialized limit checked before dispatch, and compares the requested values during the immediate inspection before start. Subsequent inspections cannot certify the environment against an earlier snapshot without accepting that configuration again. Secrets and configuration values must not appear in persistent intent, provider labels, events, operational logs, errors, process arguments or formatted debug output. Do not derive identity from plain hashes of low-entropy secrets: they can disclose values by guessing. The owner of a daemon may inspect container environment values. A saved revision or successful intent commit alone is not evidence that a daemon applied its contents.

The isolated configured path and redaction are covered by tests, and the opt-in configured adapter harness passed on the dedicated OrbStack rootless daemon using synthetic values, including creation, inspection, stop and removal. A separate backend lifecycle test in OrbStack exercised owner login, a saved digest definition, a synthetic secret, configured creation, stop, removal, stale-version rejection and idempotent repetitions; it checked the synthetic value without printing it, verified its absence from logs and state, and removed the test container. Headless Chromium on macOS at 1440×900 also exercised login, saving a definition and configuration, creation, stop and removal against the OrbStack server and worker; test resources were cleaned up. Mobile UI lifecycle tests use a simulated provider. These checks are not a full authorization review or evidence for other daemons and kernels.

## Owner authentication boundary

`internal/platform/ownerauth` provides the experimental owner-session boundary: a credential read from a private file, bounded in-memory sessions with expiration and revocation, and an `HttpOnly`, `SameSite=Strict` cookie. Protected requests additionally require a per-session token, including reads, because cookies are scoped to a hostname rather than a port; a cookie by itself is insufficient. Mutations require the exact configured origin and host. The client keeps the per-session token in memory and sends it with protected requests. Experimental server routes are guarded and the worker socket is a separate private local authority; the proxy strips session credentials before forwarding. This integration remains experimental and requires broader security review and tests at every route boundary.

Credential path checks reject unsafe ownership, permissions and symlinks in ancestors, but do not establish ACL safety and are not atomic against concurrent replacement. The operator must keep the credential and path exclusively controlled. Session state is held in memory and is revoked on process restart. These safeguards do not remove the need to protect the dedicated daemon: its administrator can inspect container environments and control that daemon.

## Server capabilities and experimental UI

The server reports the effective mode and availability via `GET /api/v1/capabilities`. Demo mode keeps simulations separate and disables real execution. In experimental mode, provider readiness includes a bounded daemon preflight; it does not prove a particular image is present or that kernel controls are effective. The UI requires owner login and confirmed availability, shows the saved revision and observed service state, and requests an explicit acknowledgement that the service has no network or public URL. A saved port is metadata and is not published. Only one initial service operation per application is supported; the UI offers a status inspection, not automatic re-creation after an uncertain outcome. Simulation pages are unavailable in experimental mode.

The browser uses an `HttpOnly`, `SameSite=Strict` cookie plus a per-session token held in memory, including for protected reads. Reload or server restart requires signing in again. A session cookie alone is not sufficient authorization. More extensive end-to-end security and recovery testing remains necessary.

## Mandatory controls before an adapter is usable

The adapter must reject operation if it cannot establish and enforce all of the following, rather than silently downgrading:

- rootless daemon and dedicated account; explicit private Unix socket, no remote TCP and no default discovery;
- numeric non-root container user, no privileged mode, all Linux capabilities dropped, `no-new-privileges`, read-only root filesystem and daemon's default seccomp and AppArmor/SELinux policy where supported;
- no devices, mounts, host namespaces, extra capabilities, published ports or network; no automatic restart;
- enforced initial maximums of 256 MiB memory, 0.5 CPU and 64 processes, and a stop grace period bounded to 10 seconds; verify host/daemon support for each limit, including rootless cgroup delegation;
- container logs disabled initially, or a separately reviewed bounded log policy; process operational logs must not include image configuration or environment;
- bounded request/response sizes, operation deadlines, no shell invocation, and sanitized error categories. Never forward the provider's raw error body.

These restrictions require verification against a real supported Linux host and daemon, including negative tests showing that unsupported controls fail closed. Engine version compatibility and endpoint semantics must be verified against the [Engine API](https://docs.docker.com/reference/api/engine/) before enabling the adapter. A fake transport verifies request construction only, not actual isolation.

## Recovery and cleanup

SQLite, the daemon and operational logs do not share a transaction. After restart, current simulated jobs are marked interrupted and are not retried. The experimental service uses persisted intent and explicitly requested inspection to reconcile an uncertain result; never blindly repeat a create after a lost response. If create succeeds but start fails, return the known reference as a partial result. Clean up only after verifying ownership and only when the caller explicitly requests it; if ownership or result is uncertain, preserve the resource and report the uncertainty.

An orphan inventory must be scoped to a verified installation identity and report candidates for review. No global prune, image deletion, automatic startup sweep, or deletion based solely on a name is allowed. Repeated stop and cleanup should be safe. Before connecting a provider, define how installation identities and operation records survive backups, and test restart, cancellation, partial failure and lost responses on the supported host. Never assume a successful database commit proves that a daemon operation occurred, or vice versa.

### Experimental reference and observation

`dockerlocal.PrepareRef` derives a stable name and a versioned fingerprint from the immutable image, revision and isolation policy before contacting Engine. The reference also carries the image and revision used to recompute that fingerprint. Inspections and mutations compare the observed immutable image ID with the locally resolved digest and require the same fingerprint; older or incomplete references are rejected. The local image must remain available for inspection; its absence is reported as provider unavailable rather than an absent container. The runtime is explicitly set to and checked as `runc`. A name is not sufficient proof of ownership. Following start or stop, the adapter also checks that the observed container ID is the one mutated. A mismatch or lost mutation response has an unknown outcome. The read-only `runtime/reconcile` package classifies an observation and never performs or authorizes a mutation, including when a resource is absent.

The isolated `runtime/intent` SQLite store persists the immutable reference and revision, a version and an observation. `prepared` means dispatch has not been authorized; `dispatched` is committed before sending a request and therefore may represent an unknown outcome; `observed` records a subsequent inspection, not permission to repeat an operation. Transitions use phase and version checks, and reject corrupt persisted rows without committing their changes. The store validates reference structure; the adapter is responsible for verifying its provider-specific fingerprint and image. It contains no secret values. File checks are not atomic and its private directory must remain exclusively controlled by the service account.

The separately invoked `runtime/recovery` component makes an explicitly invoked, bounded, serial pass over `dispatched` and `observed` intentions. It calls only `Inspect`, applies a per-inspection timeout, and records observations using the version it read. A concurrent transition is counted as a conflict, not overwritten or retried. `prepared` entries are excluded. An absent resource, failed inspection or stale observation never authorizes a new mutation. Pages are limited to 100 entries and a pass to 1,000; pagination is not a snapshot, so concurrent entries before its cursor require a later pass from the beginning. The experimental worker uses the intent store and its explicit per-service refresh performs read-only reconciliation; the separate paginated recovery component is not automatically invoked by the worker.

The experimental policy requests memory and swap limits equal to 256 MiB (no additional swap), and rejects a daemon that does not report swap control. The HTTP deadline is 15 seconds, leaving transport margin beyond the 10-second stop grace period; a caller's shorter deadline may still yield an unknown outcome. Engine's reported seccomp support does **not** prove which effective seccomp profile the daemon applies. The dedicated host must independently establish and test that policy; no real isolation claim follows from a fake Engine test. Configuration inspection is conservative and cannot establish all host properties, ACLs or runtime enforcement.

## Optional validation on a dedicated Linux host

This operator-run procedure creates one container on the explicitly selected daemon and must only be performed on a disposable, dedicated Linux host and rootless daemon. Normal Go tests use fakes and must not discover or contact a real daemon. Do not run these steps on a shared or production daemon. The commands below exercise daemon and kernel controls directly; they do not alone prove compatibility of the experimental adapter itself.

On 2026-11-01, the adapter's read-only and lifecycle harnesses passed on a dedicated OrbStack Ubuntu 24.04 ARM64 machine, kernel `7.2.12-orbstack-00394-gbecdd6130068`, Docker Engine rootless 29.9.2, cgroup v2 with the systemd driver, and a local `registry.k8s.io/pause:3.10` image pinned by digest. An independent inspection of one running adapter-created process reported `CapEff=0`, `NoNewPrivs=1`, `Seccomp=2`, non-root UID/GID, `memory.max=268435456`, `memory.swap.max=0`, `cpu.max=50000 100000`, `pids.max=64`, and loopback as its only network interface. The test container was stopped and removed. These observations apply to that one environment and process; they do not verify the precise seccomp policy, resistance to all attacks, fail-closed behavior under missing controls, or compatibility of other hosts. An independent security review remains necessary.

An optional adapter harness exists in `dockerlocal/runtimeintegration_test.go`, excluded from normal tests by the `runtimeintegration` build tag. It requires Linux, a non-root account and explicit `DARSENA_TEST_SOCKET` and `DARSENA_TEST_IMAGE` values; the image must already be local, pinned by digest, meet the adapter's restrictions and have a persistent default command so it remains running for inspection and stop. With those prerequisites established, `go test -tags runtimeintegration -v ./internal/platform/runtime/dockerlocal -run TestRuntimeIntegrationReadOnly` runs preflight and an absence check only. A separate `DARSENA_TEST_RUNTIME_MUTATE=1` opt-in enables `go test -tags runtimeintegration -v ./internal/platform/runtime/dockerlocal -run TestRuntimeIntegrationLifecycle`, which creates, inspects, stops and removes one uniquely identified container through the adapter. The test prints its reference before dispatch and preserves the resource on an uncertain result; investigate that exact reference before any action. Never set the mutation opt-in against a shared or production daemon. The tagged test skips on the macOS development host. Even a successful adapter lifecycle does not establish kernel enforcement without the independent checks below.

1. Use a non-root dedicated account with exclusive control over the daemon and every component of its private socket path. Check ownership, mode **and ACLs**; no untrusted account may replace a component. Supply the absolute socket path and a locally present, digest-pinned test image explicitly. The image must contain `/bin/sleep`, run as UID/GID 65532 with a read-only root, and declare no volumes. No pull or credentials are involved. For example, set `DARSENA_TEST_SOCKET` to the private socket path and `DARSENA_TEST_IMAGE` to the full `name@sha256:…` digest; neither value should contain secrets.
2. Confirm the host uses cgroup v2 and that the selected daemon reports Linux, rootless mode, seccomp, systemd cgroups, memory, swap, CPU and PID controls. Run the following read-only checks, then inspect the complete output manually; stop if any required capability or image metadata is absent or ambiguous. Do not rely on the Docker context or `DOCKER_HOST`.

   ```sh
   test "$(uname -s)" = Linux
   test "$(id -u)" -ne 0
   test -S "$DARSENA_TEST_SOCKET"
   stat -fc %T /sys/fs/cgroup
   docker --host "unix://$DARSENA_TEST_SOCKET" info
   docker --host "unix://$DARSENA_TEST_SOCKET" image inspect "$DARSENA_TEST_IMAGE"
   ```

   Check `cgroup2fs`, the daemon's security options, cgroup version and driver, control support, image digest and empty `Config.Volumes`. Verify the daemon's effective seccomp profile and supported LSM policy independently: an advertised seccomp capability does not establish which profile applies. Record daemon/kernel versions and evidence without recording credentials, environment values or image configuration secrets.
3. After establishing those prerequisites, create a uniquely named test container with the controls below. This is an intentional mutation of the selected daemon; retain the returned full ID for every subsequent command. If creation fails or its response is lost, inspect the exact unique name and labels before taking any action; do not rerun blindly. Choose a fresh `DARSENA_TEST_NAME` and retain it with the test record.

   ```sh
   docker --host "unix://$DARSENA_TEST_SOCKET" create \
     --name "$DARSENA_TEST_NAME" --label darsena.validation=manual \
     --user 65532:65532 --read-only --network none --restart no \
     --cap-drop ALL --security-opt no-new-privileges \
     --cgroupns private --runtime runc --memory 256m --memory-swap 256m \
     --cpus 0.5 --pids-limit 64 --log-driver none \
     --entrypoint /bin/sleep "$DARSENA_TEST_IMAGE" 300
   ```

   Set `DARSENA_TEST_ID` to the returned full ID. Inspect that exact ID and verify all requested controls, absence of mounts, devices, ports and host namespaces, the image ID and the validation label before starting. Start only that ID. Obtain its host PID from inspection, locate its cgroup v2 path via `/proc/<pid>/cgroup`, and independently read `memory.max`, `memory.swap.max`, `cpu.max` and `pids.max` from that cgroup. Confirm the numeric limits are actually enforced with controlled negative tests; inspect the running process's namespaces, capabilities, `NoNewPrivs` and seccomp state and verify network isolation. An Engine JSON field alone is not proof of kernel enforcement. Do not use unbounded load or a test that can affect other services.
4. Record success or failure separately for Engine API compatibility, unsupported controls failing closed, effective kernel isolation, memory and swap, CPU, process limit, networking, seccomp/LSM, stop timeout, restart and lost-response recovery. A manual daemon check does not establish that the adapter emits or interprets the same protocol correctly; run the separately opted-in adapter harness as another check. Lost-response and restart tests must show that no mutation is repeated automatically.
5. Stop and remove **only** the exact test container ID after independently confirming its unique name and validation label. If identity, ownership or the result of a stop/remove is uncertain, preserve it and investigate by inspection; a lost response is not proof of failure. Do not use `prune`, remove images, sweep labels globally or clean up unrelated resources. Record the cleanup outcome separately from the test outcome.
