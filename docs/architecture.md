# Architecture

The first preview has a Go HTTP process and a React frontend. The kernel registers trusted, statically compiled modules, checks their dependencies, starts them in order, and stops them in reverse order. `worker --demo` is a separate simulated process with exclusive database ownership and a private Unix socket. The local HTTP server can proxy its small job interface. It has no privileged operations.

The demo module holds bounded data in memory and advances simulated operations. HTTP exposes applications and operations under `/api/v1`; SSE delivers a complete operation snapshot on every connection and revision. A reconnect receives current state rather than a durable replay. A failed simulation preserves any previously healthy version.

The frontend uses the OpenAPI-generated types, TanStack Query, and Base UI components. It closes streams on terminal states and refreshes state on reconnect. Its data is fictional and the server is restricted to loopback.

Authentication, an outbox, integrations, real deployments, and MCP remain future work. An experimental offline backup CLI is available as described below. Neither the current kernel nor the process separation provides a security sandbox.

## Experimental persistent worker

SQLite stores simulated jobs independently from the in-memory applications. When the worker is configured, the activity screen can create and list these persistent simulated jobs. A per-database advisory lock is acquired before recovering interrupted jobs. Idempotency keys identify requests; a unique partial index prevents overlapping jobs for one resource. The worker claims queued jobs and marks interrupted running jobs on startup. The socket exposes only job creation and lookup, with bounded JSON requests and private filesystem permissions.

This is not a production authorization boundary: ownership, credential isolation, process installation, external-effect reconciliation, and a real executor remain to be designed and tested. SQLite persists worker job metadata and application definitions; the optional separate vault persists encrypted variables. Steps, events, and the UI demo remain volatile. No automatic retry follows an interrupted operation.

## Experimental encrypted configuration

An optional worker configuration vault encrypts each complete resource configuration with an external age X25519 identity. SQLite stores ciphertext, revisions, and up to 20 encrypted historical revisions. Responses omit secret values; changing a value requires the current revision. Concurrent edits conflict instead of overwriting each other.

The experimental UI can create persistent application definitions and edit variables when the vault is configured. Resource identifiers must refer to persisted application definitions. This is not integrated into deployments. The local demonstration has no production authentication: use test values only. Old encrypted revisions can retain deleted or replaced secrets. Back up the age identity separately; loss of that identity prevents recovery. Back up SQLite consistently, including its WAL, rather than copying a live database file alone. The vault database has a schema version (`user_version`, currently 1; older unversioned databases are migrated on open and keep unknown dates for earlier revisions; newer versions are rejected) and records when each revision was saved. A value-free history reports, per retained revision, which variables were added, changed or removed; any write to a secret variable counts as changed even when the value is equal, so history never reveals whether a secret matches. A single variable can be restored from a retained revision as a new revision (the value never leaves the vault), and a resource configuration with its history can be purged. Over HTTP, `GET /config/{r}/history` returns `{entries}` newest first (empty for an existing application with no configuration yet; 404 `application_not_found` otherwise), and `POST /config/{r}/variables/{name}/restore {revision, from_revision}` takes the lifecycle read lock, re-checks the application and returns the same value-free snapshot as a write. Errors: `configuration_conflict` (409, stale `revision`), `revision_not_retained` (409, pruned or unknown `from_revision`), `variable_not_in_revision` (409), `invalid_configuration` (400). Old revisions may retain secrets, so history and restore never return a value. Purging is not secure erasure: ciphertext can remain in the WAL, free pages or earlier backups, although `secure_delete` reduces this. Key rotation, secret injection, application lifecycle, and audit policy are future work.

Persistent application definitions are stored separately from the in-memory demo. Their image must be pinned to a SHA-256 digest. Creating a definition does not pull an image or start a container. Configuration endpoints require an existing persistent application ID. Definitions can be grouped into projects (single membership; deleting a project never deletes applications) and carry an integer `version` used for optimistic concurrency. The state database schema is at version 3. There is currently no deployment flow for these definitions.

The worker serves projects (`/projects`, `/applications/assign`) and edits or deletes definitions (`PATCH`/`DELETE /applications/{id}`); failures carry a stable `code`. Rules:

- The service identity of an application is fixed (`Operation: "initial"`) and runtime intentions are never deleted. Once any intention exists for an application, its image is locked (`image_locked`) and the application cannot be deleted (`application_has_service`). The port is metadata and stays editable. Edits carry the `version` they were based on (`update_conflict` otherwise); moving between projects does not bump it.
- Each application row carries a permanent `runtime_used` mark (JSON `service_used`), written inside the runtime gate right before a service creation is dispatched; if it cannot be written nothing is dispatched. Deletion and image edits are refused when the mark is set, in any mode, so a demo worker on a state directory previously used with a runtime still refuses. A creation that fails after the mark but before dispatching leaves it set (the safe side). Pre-existing installs without the mark fall back to the intention-store checks below.
- Image changes and deletion take the runtime gate without waiting (`runtime_busy` if another runtime operation holds it), so no intention can appear between the check and the change. When the runtime is enabled, the intention store is queried. When it is not, no intention database is open in this process: the worker assumes none unless a guard path was registered with `GuardIntentDB` and the file exists or cannot be inspected, in which case the change is refused with `runtime_state_unknown`. Installs that dispatched a service before the mark existed and are later opened in demo mode cannot be detected by the intention checks; do not do that.
- `GET /applications` and `GET /applications/{id}` return a summary: the definition fields plus `config` (`{revision, updated_at}` from the vault's single `Revisions` query, or null), and, with the experimental runtime, `service` (`{phase, observation, version, action?}` or null) from one read-only `ListServices` call (two SQL statements however many applications). It applies the same rules as `LastAction`: a remove action is preferred over a stop, and an invalid action row becomes `action.kind: "unknown"`. If the intention query fails, or an application's intention row is invalid, that item has `service: null, service_unavailable: true` (and `config_unavailable` likewise for the vault); the list never fails for it. The list stays a bare array, so these flags are per item. The "last change" of an application is the maximum of `updated_at` and `config.updated_at`; the service has no dates, so it does not contribute. Summaries never include variable values.
- Deletion holds the write side of a lifecycle lock while it purges the encrypted configuration and its history and then deletes the row; configuration writers hold the read side and re-check the application inside it, so no revision can be written for a deleted application. If the purge fails the definition is kept. The purge is not secure erasure (see above).


## Startup configuration

The server and simulated worker resolve explicit flags before environment variables and defaults. Worker identity and path configuration is validated before opening its persistent state. The vault opens before job recovery; opening SQLite can create or migrate files even if a later startup step fails. Filesystem prechecks are not atomic and require private directories. The age identity is read from a private file, never a command-line secret. The optional vault and job store persist data, while demo application state remains volatile. The service remains an unauthenticated loopback-only demo; configuration does not enable a real runtime.

## Health and recovery

Liveness is independent of dependency readiness. Readiness performs bounded schema access checks, not a full integrity audit. On exclusive worker startup, running jobs are marked interrupted in bounded transactions and logged individually using validated identifiers. Database commits and logs are not atomic; queued and terminal jobs are unchanged and no retry is automatic. Operational limits and recovery steps are documented in [operations.md](operations.md).

## Proposed runtime boundary

[runtime.md](runtime.md) describes the proposed isolation, recovery, and ownership requirements for a first local provider. The provider-neutral contract, experimental Docker adapter, durable intent store, execution coordinator and read-only recovery are disconnected from startup, the worker and HTTP. Tests use doubles and a simulated Engine; the adapter has not been verified against a real rootless Linux daemon or enabled. Its version 3 policy accepts certain optional collections omitted by the Engine API, while requiring explicit safety-critical controls. A demo remains a simulation, regardless of whether a daemon exists on the host.

## Experimental offline backup

`cmd/darsena-backup` snapshots the job state and optionally the encrypted vault and runtime intentions into a new private directory. It acquires the worker's state lock and uses SQLite snapshots that include committed WAL contents; restoration checks the manifest, hashes, integrity and primary schema fields (state database at schema version 2 or 3, vault at 0 or 1) before writing to a new directory. All users of every included database must remain stopped throughout: the worker lock does not protect independent vault or intent users, and snapshots of different databases are not one atomic transaction. The age identity is held separately. Checksums detect accidental corruption, not a maliciously modified manifest. The procedure and its limitations are in [operations.md](operations.md).
